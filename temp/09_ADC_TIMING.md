# RX/TX ADC — настройка и временная модель

**Источник:** PE1NNZ uSDX, commit bf8acd31b8a2506c4e1d203dfb283feecae947e1.  
**Статус:** программный порядок и номинальные datasheet timings восстановлены; первая ADC-конверсия после ADEN разобрана отдельно в [16_RX_ADC_STARTUP_TIMING.md](16_RX_ADC_STARTUP_TIMING.md). Абсолютное время ISR до ADSC и реальная I/Q aperture ещё не измерены.

## 1. ADC настройки

Исходник задаёт:

    F_ADC_CONV = 192307/2

Поскольку это целочисленное выражение, значение после препроцессора — 96 153.

Функция adc_start(adcpin, ref1v1, fs) рассчитывает ADCSRA prescaler через:

    log2(F_CPU / 13 / fs)

Затем включает ADC. Для классического AVR один conversion в steady state занимает около 13 ADC clock cycles; первая конверсия после включения может иметь более длинное время.

Исходник требует, чтобы Arduino build изначально имел F_CPU=16 MHz, затем после проверки переопределяет F_CPU на 20 007 000 Hz (фактическая частота кварца в этой конфигурации). Отдельно F_MCU по умолчанию равен 20 000 000 Hz и используется, в частности, в фазовой шкале TX. Это разные константы; смешивать их нельзя. Подробное влияние F_CPU на Timer2/Timer1 приведено ниже.

## 2. RX режим

start_rx() настраивает:
- один ADC input для отдельного TX/microphone path с параметром F_ADC_CONV*4;
- два входа I и Q с параметром F_ADC_CONV;
- сохраняет настройки каналов в admux[].

Для переопределённого F_CPU=20 007 000 Hz и fs=96 153:
- F_CPU / 13 / fs = 16;
- log2(16)=4;
- ADPS bits = 4, что соответствует делителю ADC 16;
- ADC clock ≈ 1,2504375 MHz;
- nominal 13-cycle conversion ≈ 10,396 мкс.

RX Timer2 событие повторяется каждые 16 мкс. В steady state этого достаточно, чтобы завершить conversion до следующего чтения результата, оставляя небольшой запас. Первое conversion после включения ADC может отличаться.

### Важный порядок ADMUX → ADSC → ADC

Функции сначала задают MUX и запускают следующую конверсию, а затем читают результат предыдущей:

    ADMUX = next_channel;
    ADCSRA |= (1 << ADSC);
    sample = ADC;  // result from the conversion already in progress/completed

В start_rx():
- admux[0] запоминается после выбора физического входа ADC0;
- admux[1] запоминается после выбора физического входа ADC1.

В sdr_rx_common_i():
- выбирается admux[1] и запускается следующая конверсия ADC1;
- читается результат предыдущей конверсии, которая была запущена при выборе admux[0], то есть ADC0;
- этот возвращённый ADC0 sample трактуется как I.

В sdr_rx_common_q():
- выбирается admux[0] и запускается следующая конверсия ADC0;
- читается результат предыдущей конверсии, запущенной при выборе admux[1], то есть ADC1;
- этот возвращённый ADC1 sample трактуется как Q.

Таким образом, MUX выбирает канал для будущего результата, а читаемый ADC result относится к предыдущему каналу. Кажется, что выбор каналов «перевёрнут», но это намеренная конвейерная последовательность. Если перенести только строки ADMUX без сохранения этого pipeline, можно поменять I и Q местами или нарушить фазировку.

start_rx() включает ADC, но не запускает первую конверсию: запись ADSC в adc_start() закомментирована. Первая конверсия поэтому стартует уже из первого Timer2 ISR и занимает 25 тактов ADC. При RX prescaler=16 это около 20 мкс — больше одного интервала Timer2 (около 15,994 мкс). На следующем событии ADSC ещё установлен, поэтому новая конверсия не запускается и ADC data register читается повторно. Первый результат готов лишь к следующему I-событию и физически относится к ADC1/Q, хотя попадает в логическую I-ветвь. Полная последовательность и её последствия для I interpolation описаны и протестированы в [16_RX_ADC_STARTUP_TIMING.md](16_RX_ADC_STARTUP_TIMING.md).

## 3. Временной сдвиг I/Q

Логическая последовательность ADC channel обработчиков:

    I, Q, I, Q, I, Q, I, Q, ...

Поскольку общий таймер работает на 62,5 kHz, один timer slot равен 16 мкс. Каждый отдельный канал повторяется через 32 мкс, а I/Q каналы смещены на один слот.

Функция sdr_rx_common_i() использует:

    corr_adc = (prev_adc + adc) / 2

Это двухточечная линейная интерполяция к середине между соседними I sample. Она компенсирует номинальное смещение чередующегося I/Q ввода. Однако она не доказывает, что физические sample-and-hold aperture I и Q совпадают: абсолютный момент зависит от задержки каждого ISR-пути до ADSC и фазы ADC prescaler. Эти величины пока не измерены. Кроме того, prev_adc объявлен как static и явно не сбрасывается в start_rx(); при повторном входе RX он может хранить значение предыдущего сеанса.

Точные моменты ADC sample-and-hold относительно записи ADMUX/ADSC/чтения ADC ещё нужно отразить в временной диаграмме: код читает результат предыдущей конверсии и запускает следующую, поэтому обработчик и момент аналогового измерения не совпадают.

## 4. TX режим

Для TX в start_rx() отдельный ADC channel настраивается с параметром:

    F_ADC_CONV * 4 = 384612

При переопределённом F_CPU=20 007 000 Hz:
- F_CPU / 13 / fs = 4;
- log2(4)=2;
- ADPS bits = 2, делитель ADC 4;
- ADC clock ≈ 5,00175 MHz;
- nominal 13-cycle conversion ≈ 2,599 мкс.

Это настройка скорости, с которой ADC способен выполнять преобразования, а не частота микрофонных sample frames.

В dsp_tx() при MULTI_ADC=1 выполняются четыре чтения ADC на один TX цикл. Порядок кода:

1. Читается первое значение ADC, после чего запускается следующая конверсия.
2. Отправляются подготовленные PLL-регистры Si5351 (в комментарии исходника указано около 88 мкс).
3. Читается второе значение ADC и запускается третья конверсия.
4. Вызывается ssb() с _adc, который был сформирован в предыдущем TX цикле.
5. Читается третье значение ADC и запускается четвёртая конверсия.
6. Рассчитываются новые PLL-регистры.
7. Читается четвёртое значение ADC и запускается конверсия для следующего цикла.
8. Четыре считанных значения усредняются и формируют следующий _adc.

**Важное следствие:** четыре значения, которые усредняются, не образуют равномерно расположенный во времени блок. Первое и второе чтения разделены отправкой PLL-регистров, которая в комментарии оценена примерно в 88 мкс; следующие чтения происходят после коротких участков кода ssb()/freq_calc_fast(). Поэтому нельзя заменять этот участок обычным равномерным oversampling «4 samples подряд» без проверки.

Не нужно считать, что TX микрофон получает 384,612 тысяч независимых DSP samples в секунду: это параметр настройки ADC conversion prescaler. DSP SSB вызывается один раз на TX cycle.

## 5. Pipeline задержка TX

dsp_tx() сначала использует ранее сохранённый _adc в ssb(). Одновременно в текущем вызове читаются новые ADC results, усредняются и записываются обратно в _adc.

Следовательно, обработка микрофонного сигнала и подготовка аппаратных команд конвейеризированы. В будущем нужно явно определить latency между физическим моментом ADC sample, вычислением frequency_delta/amplitude и моментом применения этих значений к выходу.

## 6. Что проверить отдельно

- Начальное состояние первого ADC conversion после adc_start().
- Точную последовательность ADMUX/ADSC/ADC register reads для RX.
- Абсолютное время analog sample-and-hold, а не только время вызова функции.
- Номинальные и фактические интервалы чтения четырёх TX ADC values.
- Задержку от среднего _adc до вызова ssb().
- Влияние source impedance и ADC acquisition time на точность измерения.
- Реальную межканальную фазовую ошибку и её компенсацию.

## 7. Фактические частоты Timer2/Timer1 после целочисленного OCR расчёта

В начале исходника проверяется, что Arduino build использует F_CPU=16 MHz. Сразу после этой проверки исходник делает undef F_CPU и задаёт:

    #define F_CPU 20007000

Комментарий указывает, что это фактический кварц около 20 MHz. Такая подмена нужна потому, что Arduino delay() и некоторые другие функции уже скомпилированы под 16 MHz и сами по себе не корректируются.

Timer2 рассчитывает OCR2A:

    OCR2A = ((F_CPU / 64) / fs) - 1

Все деления целочисленные. При F_CPU=20 007 000:
- F_CPU/64 = 312 609.
- RX target fs=62 500: 312 609/62 500 = 5; OCR2A=4.
- Фактический RX timer rate = 20 007 000 / (64*5) = 62 521,875 Hz.
- TX target fs=4 800: 312 609/4 800 = 65; OCR2A=64.
- Фактический TX timer rate = 20 007 000 / (64*65) = 4 809,375 Hz.

Соответствующие реальные интервалы:
- RX timer event ≈ 15,9944 мкс;
- одна I- или Q-выборка ≈ 31,9888 мкс;
- пара после R=4 CIC ≈ 127,9552 мкс;
- TX timer event ≈ 207,9272 мкс.

Timer1 задаёт PWM top:

    ICR1L = min(255, F_CPU / fs)

Для F_SAMP_PWM=78 125 значение F_CPU/fs получается 256, далее top ограничивается 255. При Timer1 prescaler=1 фактическая PWM carrier:

    20 007 000 / (255+1) = 78 152,34375 Hz

Таким образом, значения F_SAMP_RX/F_SAMP_TX/F_SAMP_PWM — проектные целевые частоты, а реальный timer rate определяется целочисленным OCR/top. Это небольшие, но измеримые отличия.

### Важное TX расхождение

При стандартном F_MCU=20 000 000 исходник получает _F_SAMP_TX=4 800 для расчёта фазовой шкалы. Фактический Timer2 TX rate из OCR формулы около 4 809,375 Hz. Это расхождение примерно 0,195%.

Нельзя самостоятельно исправлять его при первом переносе. Сначала нужно решить, что является эталоном: точное поведение исходного устройства или номинальная математическая шкала F_SAMP_TX. Сохранение исходного поведения — базовый ориентир; любое изменение оформить отдельным вариантом и проверить спектром/частотным измерением.

Источники: [F_CPU override](https://github.com/threeme3/usdx/blob/bf8acd31b8/usdx.ino#L130-L143), [timer1_start/timer2_start](https://github.com/threeme3/usdx/blob/bf8acd31b8/usdx.ino#L3295-L3330), [переключение частоты Timer2 RX/TX](https://github.com/threeme3/usdx/blob/bf8acd31b8/usdx.ino#L3695-L3705).

## 8. Исполняемая ADC input model

Программная часть MUX/read-previous и midpoint interpolation I вынесена в:
- [rx_adc_input.py](reference/rx_adc_input.py)
- [test_rx_adc_input.py](reference/test_rx_adc_input.py)

Полная доступная SSB цепочка, начиная с значений analog I/Q для каждого Timer2 event, собрана в:
- [rx_ssb_adc_chain.py](reference/rx_ssb_adc_chain.py)
- [test_rx_ssb_adc_chain.py](reference/test_rx_ssb_adc_chain.py)

В модели параметр startup_adc_register позволяет задать содержимое ADC data register на первом чтении после start_rx(). По умолчанию он равен нулю только для тестового удобства; исходный код не гарантирует это значение.

Входные I/Q values трактуются как значения, захваченные conversion, стартовавшей на соответствующем Timer2 event. Точный analog sample-and-hold aperture внутри conversion, acquisition settling и jitter пока не моделируются. Это остаётся отдельной аппаратно-временной задачей перед выбором фактического ADC/codec на ESP32.


## 9. Startup conversion и sample-and-hold

После сверки с даташитом ATmega328P выяснилось, что прежняя логическая модель rx_adc_input.py не воспроизводила задержку первой конверсии после ADEN. Добавлена отдельная цикл-тактовая модель reference/rx_adc_timing.py и тесты reference/test_rx_adc_timing.py. Она показывает два чтения старого ADC data register, первый Q результат, ошибочно принятый за I, и ещё одну загрязнённую midpoint-интерполяцию I. Детальный расчёт, допущения и временная таблица: [16_RX_ADC_STARTUP_TIMING.md](16_RX_ADC_STARTUP_TIMING.md).
