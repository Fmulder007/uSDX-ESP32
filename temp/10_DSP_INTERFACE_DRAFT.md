# Черновик интерфейса независимого DSP-ядра

**Статус:** проектный черновик; интерфейс ещё не утверждён и код не реализован.  
**Основа:** активные RX/TX алгоритмы PE1NNZ uSDX, commit bf8acd31b8a2506c4e1d203dfb283feecae947e1.  
**Назначение:** провести чёткую границу между математикой и ESP32-периферией.

## 1. Главный принцип

DSP должен быть обычным вычислительным модулем. Он получает заранее подготовленные цифровые отсчёты, обновляет собственное состояние фильтров и возвращает цифровые результаты.

DSP не должен:
- читать ADC напрямую;
- управлять I2S, DMA или GPIO;
- обращаться к Si5351 по I2C;
- записывать PWM-регистры;
- вызывать Serial, OLED, Wi-Fi или файловые операции;
- использовать delay(), millis() или ожидание аппаратного события внутри математики;
- выделять динамическую память на каждом sample/block.

Аппаратные адаптеры могут быть заменены без переписывания DSP.

## 2. Предлагаемые программные уровни

    ADC/I2S/DMA input

Это функциональная схема, а не выбор конкретной периферии.

## 3. RX input — три варианта

### Вариант RX-A: исходные чередующиеся ADC events

Входное событие содержит:
- channel: I или Q;
- sample: центрированное знаковое значение;
- последовательный номер события или временную метку.

Пример структуры:

    enum class RxChannel : uint8_t { I, Q };

    struct RxAdcEvent {
        RxChannel channel;
        int16_t sample;
        uint32_t sequence;
    };

DSP обрабатывает события строго по порядку исходного расписания. Внутри DSP находятся выравнивание I, CIC-фазы, Hilbert и дальнейшая обработка.

Преимущества:
- наиболее прямо воспроизводит исходную одноканальную ADC-модель;
- сохраняет взаимный временной сдвиг I/Q;
- проще сравнить с оригинальной фазовой последовательностью.

Недостатки:
- интерфейс отражает конкретный способ захвата uSDX;
- при синхронном dual ADC потребуется адаптер, который создаёт эквивалентный поток.

### Вариант RX-B: массивы I[] и Q[]

Адаптер передаёт два массива отсчётов на канал. До DSP необходимо точно определить:
- временно одновременны ли I и Q;
- применена ли коррекция половины интервала;
- одинаковы ли sample count и временная база.

Преимущество — удобный блочный интерфейс. Недостаток — временное отношение исходных каналов становится неявным, если не сопровождать блок метаданными.

### Вариант RX-C: source-aligned I/Q pairs

Адаптер передаёт уже временно выровненные пары. Это удобная граница, но адаптер обязан воспроизвести эквивалент исходной коррекции между I и Q. Если этого не сделать, изменится фаза и боковое подавление.

**Предварительная рекомендация:** внутри эталонного DSP оставить RX-A как базовый вход. Разрешить block wrapper, который принимает массив RxAdcEvent и последовательно подаёт их в ту же внутреннюю state machine. Так sample-by-sample и block tests используют одну математику.

## 4. RX output

После CIC/Hilbert/demod/AGC/NR/IIR DSP выдаёт один аудиоотсчёт на каждую готовую пару I/Q. Номинальная частота — 7 812,5 samples/s; фактическую базу и тайминг исходного Timer2 отдельно фиксируем в ADC timing документе.

Предлагается разделить:
- DSP_RX output: моно PCM sample до выходного интерполятора;
- DSP_AUDIO_OUT: source-compatible Comb/integrator interpolation либо иной отдельно тестируемый output DSP;
- audio adapter: передача подготовленного аудио в I2S DAC/PWM/codec.

Так можно сначала сравнивать демодулятор без привязки к конкретному аудиовыходу.

## 5. TX input/output

### TX input

DSP_TX получает один нормализованный микрофонный отсчёт, соответствующий входу ssb() исходной реализации.

В исходнике MULTI_ADC собирает и усредняет четыре результата ADC, после чего формирует _adc. Где выполнить это усреднение — в mic input adapter или отдельном DSP pre-stage — пока отдельный выбор. Важно, чтобы на вход ssb-equivalent функции приходило то же численное значение и в том же временном порядке.

### TX output

Предлагаемая структура результата:

    struct TxDspOutput {
        int16_t frequency_delta;
        uint8_t amplitude;
    };

frequency_delta — численная команда изменения частоты в единицах, ожидаемых RF adapter после проверки масштаба исходника. amplitude — управляющий уровень PA.

DSP_TX не знает, как передавать эти значения в Si5351/PWM. RF adapter отвечает за:
- применение pipeline/delay, совместимого с исходником;
- подготовку и отправку PLL-регистров;
- обновление PA PWM;
- очередность и временную привязку команд.

Отдельно должны быть проверены один sample delay в исходном TX pipeline и разница nominal/actual Timer2 rate.

## 6. Состояния

Предлагаемые явные контексты:

- RxDspState — CIC, Hilbert, I delay, demod, AGC, NR, IIR и статистика.
- TxDspState — mic filter, 16-value history, phase history, amplitude state и параметры.
- AudioOutState — состояние выходного интерполятора.
- DspConfig — mode, filter, AGC, volume, NR, drive и другие параметры, задаваемые извне.

Никакие фильтры не должны прятать состояние в локальных static переменных. Каждая переменная состояния должна иметь владельца, документированный тип и функцию инициализации.

### Жизненный цикл

Черновые операции:
- cold_init() — состояние после включения/полного старта;
- source_compatible_resume_rx() — воспроизводит исходное поведение при возврате из TX в RX, включая сохранённые CIC/Hilbert state;
- reset_rx_all() — полный сброс RX state для тестов/отдельного режима;
- reset_tx_all() — полный сброс TX state.

Эти операции не взаимозаменяемы. Наблюдаемое поведение исходника описано в 03_STATE_AND_TIMING.md.

## 7. Sample API и block API

Возможный внутренний минимальный интерфейс:

    void rx_process_event(const RxAdcEvent& event,
                          RxAudioSample* output,
                          bool* output_ready);

Возможная блоковая оболочка:

    size_t rx_process_events(const RxAdcEvent* input,
                             size_t input_count,
                             RxAudioSample* output,
                             size_t output_capacity);

Block wrapper должен вызывать ту же последовательную обработку событий, а не содержать независимую реализацию CIC. Это помогает проверить идентичность результатов для одного и того же входа при обработке одним sample и несколькими блоками.

Для TX:

    TxDspOutput tx_process_mic_sample(int16_t normalized_sample);

Типы в примере предварительные. Точная ширина аккумуляторов и правила округления будут определены после численной проверки AVR/ESP32.

## 8. Варианты расписания DSP на ESP32

- Sample-by-sample: один event вызывает одну короткую ступень state machine. Удобно для reference test, но не обязательно для окончательной реализации.
- DMA block: обработка последовательного массива событий; latency определяется размером блока.
- Hybrid: DMA/ISR принимает данные, DSP task обрабатывает готовые блоки из ring buffer.

Предварительный кандидат — hybrid/block для целевой прошивки и sample-by-sample для эталонных тестов. Финальный выбор только после измерения WCET, buffer latency и качества I/Q sampling.

## 9. Что нельзя решить до эталонных тестов

- Точный формат и диапазон входного ADC sample.
- Нужна ли коррекция I внутри DSP или в input adapter для конкретного ADC.
- Точные accumulator widths и wrap/saturation semantics.
- Возвращать ли в DSP_RX выходной интерполятор или оставить отдельным DSP_AUDIO_OUT.
- Допустимая блочная задержка и размер блока.
- Точная задержка frequency_delta до аппаратного применения Si5351.

## 10. Следующий шаг

Перед реализацией API подготовить host-side reference harness:
1. подать одну и ту же последовательность raw RX events в sample и block API;
2. сохранить промежуточные значения CIC, Hilbert, demod и финальный audio;
3. сравнить с исходной моделью;
4. аналогично сравнить TX mic input → frequency_delta/amplitude;
5. после этого окончательно выбрать сигнатуры и типы данных.

Этот файл фиксирует проектный черновик и варианты. Это не утверждённый API и не начало портирования.
